## 总体判断

**设计扎实、可直接指导实施，有两处需细化。** 建议稿的五级流水线与现有实现踩过的坑高度吻合，原则层无根本性缺陷。L3 段落检索和 L5 引用校验是主要新增工作量，上下文预算假设需保守修正。

## 需细化或存疑

### 1. L3"范围内全文检索"边界模糊，工作量被低估

建议稿说"在 L2 命中条目内做段落级全文检索"，但：

- 现有代码 L2 验收后直接展示全文，**无段落级切分→片段提取**这一步
- 落地需要：(a) 页面章节锚点结构化（`extractTocFromLines` 可复用）；(b) 段落级切分+~500字窗口检索；(c) 片段→章节归属关系维护
- 建议稿写得太轻，实际工作量约等于新建一整层检索逻辑

**建议**：L3 单独拆出实施阶段，S2 阶段先做 L1+L2+L4+L5（无 L3），验证元数据检索+引用校验的端到端效果。若元数据召回已够用则 L3 可推迟。

### 2. 上下文预算"数万 token"假设偏乐观

本地可部署 7B 模型（Qwen2.5-7B 等）实际可用上下文约 4K-8K token（非厂商宣传的 32K/128K）。建议稿 L3 控制"≤30 片段 × ~500 字 ≈ 15K 字 ≈ 20K token"，7B 模型一次吃不下。

**建议**：
- 明确 L4/L5 分批送入，每批 ≤4K token 输入
- 或按条目级验收（L4 一次送 5-10 条元数据），而非片段级
- 申报书修改建议第 4 条的措辞"数万 token 级"改为"数千 token 级"更保守但更诚实

### 3. COMPOUND_PREFIXES 维护成本

ICU 领域复合实体量大且持续更新（"社区获得性肺炎""医院获得性肺炎""AECOPD""SA-AKI"等），纯手工维护清单+回归测试负担重。

**建议**：补充 LLM 辅助生成候选清单 + 人工审核的工作流，而非纯手工维护。

### 4. 评测集 30-50 查询统计置信度偏低

对"引用校验通过率 ≥95%"指标，30-50 条查询产出的建议条目约 100-200 条。统计上 95% 置信区间宽度约 ±3%，实际可能 ±5-6%。

**建议**：至少 100 查询，或分轮扩充（第一轮 50 建基线，第二轮扩至 100+ 做回归）。

## 对申报书修改建议的修正意见

建议稿第 7 节四处增补基本同意，但对第 4 条有修正：

- 原文："受限于本地可部署模型的可用上下文（数万 token 级）"
- **建议改为**："受限于本地可部署模型的可用上下文（数千 token 级），无法将知识库全量送入模型，必须分级收窄、分批验收"

理由：7B 模型实际可用上下文远低于厂商宣传值，用"数万"会误导评审。

## 实施优先级建议

1. **S2-first**：L1+L2+L4+L5（跳过 L3），验证元数据检索+引用校验端到端效果
2. **S2-second**：若元数据召回不够，补 L3 段落检索
3. **S2-parallel**：RULE_SEARCH_HINTS 症状定向词 + 评测集建设
4. **S3**：评测跑通四项指标 + 模型调优

这个顺序的好处是：L3 是最大的不确定性（工作量+效果），推迟到有数据验证时再做，避免过度工程。
