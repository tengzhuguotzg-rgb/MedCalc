## 一、项目现状

### 1.1 规模

| 维度 | 数值 |
|---|---|
| ArkTS 代码 | 34,269 行（160 个 .ets 文件） |
| 计算器 | 88 个（UI 组件 85 个 + 引擎函数 93 个） |
| 服务层 | 10 个文件，6,464 行 |
| 知识库 | 数千篇 Markdown，FTS4 全文检索 |
| 技术栈 | ArkTS + ArkUI + HarmonyOS 6.0.2 (API 22) |
| 第三方依赖 | 零运行期依赖 |
| 单元测试 | 零（hypium/hamock 已是 devDependency 但从未使用） |

### 1.2 功能模块

- **计算器 Tab**：88 个 ICU 临床计算器，三模式切换（常规模式/LLM推荐/LLM识别）
- **病历 Tab**：患者管理 + RDB 持久化 + 全量预警引擎 + 诊断规则匹配 + LLM 诊断确认
- **知识库 Tab**：SQLite FTS4 全文检索 + LLM 扩展检索 + Markdown 渲染器
- **设置 Tab**：LLM 配置 + 主题切换
- **AI 推荐计算器**：R1 固定问卷 + R2 LLM 自由追问 + 弹出计算器 + 结果回填
- **AI 助手**：上传图片/PDF -> LLM 提取结构化数据 -> 自动匹配计算器

### 1.3 后续要做的功能

1. **独立诊断 Tab**：ICD-11 基座 + 76 个疾病实体 + LLM 驱动指南建议
2. **诊断 Tab 与病历打通**：病历页诊断板块复用诊断 Tab 的基座和指南内容
3. **指南动态更新**：临床医生只需往知识库扔指南文件，LLM 自动提取

## 二、架构问题评估

### 2.1 评分

| 维度 | 分数 | 说明 |
|---|---|---|
| 功能完整度 | 8/10 | 88 计算器 + AI 推荐 + 病历 + 知识库 |
| 代码组织 | 4/10 | Index.ets 上帝文件、AssistantService 1718 行怪兽 |
| 可维护性 | 4/10 | 新增计算器要改 6 处、两份 if-else 同步 |
| 类型安全 | 9/10 | 零 any，接口定义清晰 |
| 视觉规范 | 7/10 | color.json 双主题 + 语义 token，但有 emoji 混用、遮罩不统一等遗留 |
| 架构一致性 | 5/10 | 引擎/UI 分离好，服务层职责混乱，LLM 协议分散 |
| UI 美学/交互 | 5/10 | 功能完备但缺少 Toast 反馈、Sheet 高度一刀切、图标体系不统一 |
| **综合** | **5.4/10** | 功能强但技术债重，UI 有改善空间 |

### 2.2 核心问题清单

#### P0 - 阻碍扩展的硬伤

**问题 1：Index.ets 上帝文件（845 行，15 个职责）**

- 88 路 if-else 路由 ×2 份（CalcModeView 行 241-419 + CalcSheetBuilder 行 492-668），完全复制
- 96 行 import（88 个计算器组件全部静态导入）
- 同时承担 Tab 容器、导航栈、模式切换、收藏管理、偏好持久化、Sheet 宿主、Topbar 等 15 个职责

**问题 2：AssistantService.ets 怪兽（1718 行）**

- 4 个巨型字典（DATA_FIELDS 140条 + CALC_ID_ALIASES 130条 + FIELD_KEY_ALIASES 65条 + CALC_INPUT_SPECS 85条）占 48%
- callEngine 330 行 84 个 if-else 分支
- fallbackParse 130 行硬编码正则
- 新增计算器要改 6 处

**问题 3：注册表驱动不彻底**

- Calculator 接口有 `compute: string` 字段，88 个条目都填了值，但全工程零读取
- CALC_ID_ALIASES（130 条）作为旁路字典存在，注册表不是唯一数据源
- CALC_INPUT_SPECS（85 条）也是旁路字典，与注册表并列

#### P1 - 影响维护的债务

**问题 4：KnowledgeService.ets（1568 行）**

5 个子领域混在一个文件：DB 初始化 + Markdown 摄取 + FTS 检索 + LLM 增强检索 + UI 接口

**问题 5：LLM 协议分散**

- extractJsonPayload 三层防护工具只有 AssistantService 用
- PatientService 和 KnowledgeService 各自写 JSON 解析
- 三个服务的 LLM prompt 各自硬编码在方法体内

**问题 6：AppStorage 无类型消息总线**

- `sheetCalcId/Value/Tier/TierClass/ValueText/Unit/Timestamp` 7 个裸键
- `llmRec*` 5 个裸键
- 无封装、无类型安全

**问题 7：魔法数字/字符串泛滥**

- currentTab 用 0/1/2/3，无枚举
- calcMode 用 'normal'/'recommend'/'recognize'，无枚举

#### P2 - UI 美学与交互体验

**问题 8：图标体系不统一**

emoji（🗑💬➤⤢✅×⚠✕）与 SVG 图标混用，视觉风格不一致

**问题 9：遮罩 rgba 取值不统一**

至少 4 种取值（0.35/0.4/0.15/0.25），缺少统一 token

**问题 10：无 Toast/成功反馈**

全工程无 showToast，错误横幅不自动消失

**问题 11：bindSheet 高度一刀切**

固定 SheetSize.LARGE，2 个输入框的简单计算器浪费 60% 屏幕

**问题 12：顶栏 token 名不副实**

headerBg token 在 color.json 里仍是白色，commit 宣称的"深青顶栏"未落地

## 四、诊断基座存储选型判据

> 此决策不阻塞阶段 1-2，但阶段 2 动手前应定案。

| 内容 | 生命周期 | 存储方式 |
|---|---|---|
| ICD-11 编码 + 76 疾病实体框架 | 变化以年计 | 代码常量 |
| 诊断标准阈值（如 SOFA≥2） | 随指南版本更新 | 代码常量（跟随版本发布） |
| "实体 -> 指南章节"映射关系 | 随指南补充而增长 | SQLite（可增量更新） |
| 指南建议文本（四类内容） | LLM 动态生成 | 不入库（缓存到 Preferences） |

按"LLM 驱动 + 指南约束"架构：指南建议由 LLM 从知识库动态生成不入库，但"实体 -> 指南章节"的映射关系会随指南补充而增长，需要数据库支持增量更新。

## 五、重构计划

### 设计原则

1. **ArkUI 约束优先**：所有方案必须通过 `devecocli build` 编译验证
2. **渐进式重构**：每个阶段独立可验证，不一次性大改
3. **为诊断 Tab 铺路**：重构优先级服务于后续诊断 Tab 功能
4. **结构重构与 UI 改动分离**：结构重构阶段不改可见行为，UI 改动独立阶段做（避免回归归因困难）
5. **每阶段一个 git 分支 + 手动验证 checklist**

### 执行顺序

```
阶段 0（单测网）→ 阶段 1（CalcRouter）→ 阶段 2（拆 AssistantService + 注册表合并 + 总线封装）
→ 阶段 4（枚举化）→ 阶段 3（拆 KnowledgeService）→ 阶段 5（UI 美学与交互体验）
```

### 阶段 1：消除 if-else 路由重复

**目标**：Index.ets 的 88 路 if-else × 2 份 -> 1 份共享路由

**方案**：

新建 `components/CalcRouter.ets`：
- 做成 `@Component struct`，用 `@Prop calcId: string` 接收
- 从 Index.ets 迁移 88 个计算器组件 import
- if-else 链放在 `build()` 里（ArkUI 限制，if-else 是唯一可行方案）
- 包含 else 分支的 PlaceholderCalculator

改造 `Index.ets`：
- 删除 96 行 import（迁移到 CalcRouter）
- CalcModeView 里 88 路 if-else 替换为 `CalcRouter({ calcId: this.currentCalc })`
- CalcSheetBuilder 里 87 路 if-else 替换为 `CalcRouter({ calcId: this.sheetCalcId })`
- 从 845 行减至约 400 行

**关于映射表方案的说明**：

通用前端的 `Record<string, Component>` 映射表在 ArkUI 里不可行（@Component struct 不是一等公民）。`wrapBuilder` 理论上可包装 @Builder 为 WrappedBuilder，但只支持顶层 @Builder 函数不支持 @Component struct，需 spike 验证。当前方案用 @Component struct + @Prop 是 100% 可行的。

**验证标准**：
- `devecocli build` BUILD SUCCESSFUL
- 88 个计算器在常规模式和 Sheet 模式下都能正常渲染

**预计改动**：
- 新建 1 文件（CalcRouter.ets，约 200 行）
- 改造 1 文件（Index.ets，845 -> ~400 行）

### 阶段 2：拆分 AssistantService + 注册表合并 + 总线封装

**目标**：1718 行 -> 拆成 4 个文件，新增计算器从改 6 处降至改 3 处，注册表成为唯一数据源

**方案 A：拆分 AssistantService**

新建 `model/FieldSchema.ets`：
- 迁移 `DATA_FIELDS`（140 条）
- 迁移 `FIELD_KEY_ALIASES`（65 条）
- 迁移 `normalizeFieldKey` / `normalizeForSearch`

新建 `services/CalcDispatcher.ets`：
- 迁移 `callEngine` 的 84 个 if-else
- 用 `Record<string, (data: Map<string,string>) => CalcResult | null>` 策略表替代（ArkTS 普通函数是一等公民，此方案可行）
- 单位换算函数集中（Cr 88.4、Bili 17.1、BUN 2.8、FiO₂ %↔小数）
- 闭包共享 `n()/s()/b()` 辅助函数

改造 `AssistantService.ets`：
- 删除迁移出的数据声明和 callEngine
- 只保留对话管理 + LLM 提取 + 消息构建
- 从 1718 行减至约 500 行

**方案 B：注册表合并（单一数据源）**

改造 `model/CalculatorRegistry.ets` 的 Calculator 接口：

```typescript
export interface Calculator {
  // 现有字段
  id: string;
  name: string;
  enName: string;
  group: string;
  icon: string;
  shortcut: string;            // Sidebar 快捷键用
  kw: string;
  description: string;
  whenToUse: string;
  reference: string;
  // 新增字段
  aliases: string[];           // 原 CALC_ID_ALIASES 的内容，按计算器归入
  inputSpec: CalcInputSpec;     // 原 CALC_INPUT_SPECS 的内容，按计算器归入
  compute: string;              // 复活为 CalcDispatcher 策略表的键
}
```

- `CALC_ID_ALIASES`（130 条）并入每个 Calculator 的 `aliases` 字段
- `CALC_INPUT_SPECS`（85 条）并入每个 Calculator 的 `inputSpec` 字段
- `compute` 字段从死字段复活为 CalcDispatcher 策略表的查找键
- 注册表成为每个计算器唯一的事实来源

**实施注记（aliases 查询性能）**：LLM 输出归一化是高频调用，原来 `CALC_ID_ALIASES` 是 O(1) 字典查找。并入 `aliases: string[]` 后若每次线性扫描是 O(88×n)。实施时应以注册表为单一数据源、启动时派生一个反向 Map 缓存（`aliasToCalcId: Map<string, string>`），数据源唯一和查询效率兼得。

新增计算器变为 3 步：
1. 注册表加 1 条（含 aliases + inputSpec + compute）
2. 引擎加 1 函数
3. CalcRouter 加 1 分支（ArkUI 限制，无法避免）

**方案 C：AppStorage 总线封装**

新建 `services/SheetResultBus.ets`：
- 封装 `sheetCalcId/Value/Tier/TierClass/ValueText/Unit/Timestamp` 7 个键

- 注意：写入端在 `CalcWidgets.ets` 的 ResultCard（行 160-177），此文件头部注释写着"禁止顺手优化以保持视觉一致"，改动需独立 commit + 逐像素核对

## 七、ArkUI 框架约束说明

以下是 ArkUI 与通用前端框架的关键差异，直接影响重构方案选择：

1. **`@Component struct` 不能当值传递**：不能 `const comp = CrClCalculator`，不能 `Record[key]()` 动态调用。if-else 是唯一可行方案。
2. **`@Builder` 是编译时宏**：不能跨组件调用（不能从 Index 调用 CalcRouter 的 @Builder）。需用 @Component struct + @Prop 替代。
3. **`@State` 只能在 `@Component struct` 内使用**：不能在普通 class 里用响应式状态。
4. **不支持继承**：@Component 不能继承，不能用基类 + 模板方法模式。
5. **`@BuilderParam` 可以接收回调**：父组件可以传 @Builder 函数给子组件，但仍是编译时绑定。
6. **`wrapBuilder(fn)` 可以包装 @Builder 为 WrappedBuilder**：理论上可构建映射表，但只支持顶层 @Builder 函数，不支持 @Component struct。需 spike 验证。
7. **条件渲染 if/else 会销毁/重建组件**：切换分支时旧组件被卸载、新组件被创建，状态不保留。resetKey 机制正是利用此特性强制清空非受控 InputRow。
8. **普通 TypeScript 函数是一等公民**：可以当值传递、可以构建 Record 策略表。callEngine 的策略表方案可行。
